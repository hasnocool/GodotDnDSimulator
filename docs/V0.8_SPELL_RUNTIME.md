# v0.8 Spell Runtime

v0.8 adds deterministic, data-driven spellcasting on top of the existing rules, actor, combat,
spatial, bridge, and Godot tactical-client layers. It does **not** add spell-name conditionals to the
runtime and does not move casting legality into Godot.

## Authority and composition

The authoritative flow remains:

```text
Godot spell choice / target / point / direction
  -> spells.preview
  -> authoritative rules + spatial validation
  -> tactical.cast_spell
  -> SpellRuntime
       -> v0.3 RulesRuntime for d20 tests, saves, modifiers, target selectors
       -> v0.4 ActorState for abilities, saves, tags, conditions, resources
       -> v0.5 CombatRuntime for action spending, damage, healing, conditions
       -> v0.6 SpatialQueryService for distance, LOS and area membership
  -> fresh tactical snapshot + resolved presentation events
  -> Godot presentation
```

Godot may render the returned target list, area cells, spell resources, concentration state, and
resolved events. It must not decide whether a target is in range, visible, in an area, affected by a
save, damaged, healed, conditioned, or otherwise legal.

## Spell definitions

`godot_dnd_engine.spells.SpellDefinition` is generic data. A definition contains:

- stable spell ID and display name;
- spell level and preparation requirement;
- automatic, attack-roll, or save resolution;
- self, creature, point, or area target mode;
- range and maximum-target metadata;
- optional v0.3 `TargetSelector` for tag-based eligibility;
- generic damage, healing, condition, and condition-removal effects;
- optional save-for-half or save-negates behavior;
- optional concentration and finite round duration;
- generic sphere, cube, cylinder, cone, or line area metadata;
- slot-level scaling for damage dice, healing dice, and target count.

The runtime never switches on a spell ID. The original `spell:*` fixtures in `spell_slice.py` exist to
exercise effect families and the Godot workflow; they are project-owned demo content rather than
copied rules text.

## Caster state and slots

`SpellcastingState` stores, per actor:

- casting ability;
- spell attack bonus;
- spell save DC;
- known spell IDs;
- prepared spell IDs;
- levelled `SpellSlotPool` values;
- current concentration state.

Cantrips use cast level 0 and do not consume slots. Levelled spells require an available slot at or
above their base level. A cast at a higher level uses the selected slot and applies only the generic
scaling declared by the spell definition.

## Resolution

### Spell attacks

Spell attacks use the existing deterministic v0.3 d20 resolver. The caster's configured spell attack
bonus is represented as a generic modifier over the casting ability. The target armor class comes from
the v0.4/v0.5 combatant state. All random rolls use the shared versioned engine RNG.

### Saving throws

Save spells use `RulesRuntime.resolve_save()` with the target actor's ability score and save
proficiency and the caster's spell save DC. Effects can declare no save adjustment, save-for-half, or
save-negates behavior.

### Damage, healing, and conditions

Spell effects delegate to `CombatRuntime`:

- damage uses the existing damage/defense/HP pipeline;
- healing uses the existing healing/life-state pipeline;
- conditions use the existing combat condition event/reducer path;
- condition removal uses the existing removal path.

Spell code does not implement a second HP, defense, or condition system.

## Spatial targeting and areas

Creature targets are checked with authoritative distance and LOS queries. Area targets are delegated
to the v0.6 generic area query surface and return authoritative cells and entity IDs. The Godot client
renders those returned cells and IDs; it does not recompute area membership.

Cone and line definitions accept a direction supplied as player intent. Choosing a direction is a
presentation/input action; deciding which cells/entities the shape contains remains spatial-authority
work.

## Concentration and durations

Only one concentration spell can be active for a caster. Beginning another concentration spell ends
the previous concentration state and removes its runtime-owned active effects. A concentration check
uses the existing Constitution saving-throw path; failure ends concentration and associated duration
state.

`ActiveSpellEffect` tracks finite ongoing effects by stable effect ID, caster, targets, generic effect
specifications, remaining rounds, and concentration ownership. Round advancement can apply explicitly
ongoing effects and expire duration-owned conditions without blocking combat progression.

## Events and serialization

`SpellEvent` v1 provides an ordered spell-runtime event surface. Canonical JSON-shaped serialization is
validated by `schemas/v1/spell-event.schema.json`. Spell events are separate from the v0.7 client
presentation messages: domain/runtime events describe spell state transitions, while
`tactical.spell_resolved` and related presentation events tell Godot how to present already-resolved
results.

## Query and bridge API

`SpellQueryService` exposes JSON-shaped read-only operations:

- `spells.available` — known/prepared/castable spells, legal slot levels, slots, concentration;
- `spells.state` — current slots, concentration, and active effects;
- `spells.preview` — authoritative cast preview including resolved target IDs and authoritative area
  cells/entity membership where relevant.

The v0.8 default `godot-dnd-client-bridge` host advertises additive capabilities:

- `spells.runtime.v1`;
- `spells.commands.v1`;
- `spells.queries.v1`;
- `spells.previews.v1`.

The typed authoritative command is `tactical.cast_spell`. While the tactical provider is active, the
bridge rejects unrelated core simulation commands so one client session cannot accidentally maintain
two competing authoritative state streams.

## Godot UI

The Godot tactical scene subclasses the v0.7 presentation controller and adds a data-driven spell
palette. The palette is activated only when the authoritative tactical snapshot contains spellcasting
state, preserving compatibility with v0.7-only providers.

For each engine-provided spell/slot option the client:

1. enters the existing C3 target or shape-preview mode;
2. submits `spells.preview` with caster, selected slot, target IDs and/or point/direction intent;
3. renders only returned authoritative targets/area cells;
4. arms `tactical.cast_spell` only when the preview says the intent is legal;
5. reconciles to the fresh authoritative snapshot after acceptance;
6. maps resolved spell presentation events to generic log, emphasis, and audio hooks.

There are no named-spell branches in GDScript.

## Test matrix

The v0.8 focused suites cover:

- known/prepared spell and slot discovery;
- cantrip casting without slot consumption;
- higher-slot upcasting;
- attack-roll spells;
- save/AoE previews and casts;
- v0.3 target-selector composition;
- concentration replacement;
- duration/ongoing-effect state;
- spell-event serialization and JSON Schema conformance;
- bridge capability/query/preview/command delegation;
- prevention of dual authoritative streams;
- Godot spell palette and preview-before-command behavior using `FakeEngineTransport`;
- authoritative area-cell visualization.

The repository executable gate remains `scripts/local_ci.sh`. Implementation checkboxes may be marked
complete before the exact branch executes that gate, but the v0.8 exit criterion must remain open until
Ruff, strict Mypy, pytest/coverage, governance/schema checks, importer determinism, and all headless
Godot suites pass on the integrated head.
