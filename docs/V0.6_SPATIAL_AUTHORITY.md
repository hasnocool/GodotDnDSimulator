# v0.6 Spatial Authority

v0.6 adds a deterministic, headless tactical spatial authority under
`engine/src/godot_dnd_engine/spatial/`. It builds on the v0.4 shared actor model and v0.5 tactical
combat runtime without moving rules authority into Godot navigation or scene state.

## Ownership boundary

The spatial package owns authoritative answers for:

- logical tactical cells and bounded spaces;
- multi-cell entity footprints and occupancy;
- collision/occupiability;
- distance and reach queries;
- movement-mode compatibility;
- path legality and deterministic pathfinding;
- movement cost and difficult terrain;
- elevation-aware movement;
- reachable-space queries;
- line of sight and visibility blockers;
- cover classification from logical spatial data;
- generic sphere/cube/cylinder/cone/line area membership;
- geometric threat-zone enter/exit inputs;
- validation of navigation paths proposed by presentation adapters;
- replayable spatial movement facts.

It does **not** own:

- initiative, turns, action economy, or reaction spending;
- attack, damage, save, condition, or spell resolution;
- Godot meshes, physics bodies, navigation meshes, cameras, or scene nodes;
- animation/VFX/audio;
- named spell or ability behavior.

v0.5 remains authoritative for combat turn/action accounting. Godot may propose geometry/navigation
observations, but this package is the tactical legality authority.

## Logical space

`LogicalSpace` is the backend-independent interface. The initial implementation is
`SquareGridSpace`, a bounded two-dimensional logical grid with per-cell elevation.

`TerrainCell` can describe:

- a stable terrain ID;
- elevation in feet;
- difficult terrain;
- movement-blocking collision;
- LOS-blocking obstacle height;
- an explicit cover classification;
- movement modes permitted through that logical cell.

The model is intentionally not tied to Godot units or a navigation mesh. Future graph, hex, or
continuous adapters can satisfy the same logical-space role without changing client authority.

## Occupancy and footprints

`SpatialPlacement` stores a stable engine entity ID, anchor cell, height, collision/LOS behavior,
cover metadata, and an explicit tuple of footprint offsets.

A footprint can occupy multiple logical cells. `SpatialState` rejects out-of-bounds blocking
placements, duplicate entity IDs, blocking overlap, and invalid placement on blocked logical terrain.

Placement state is immutable. Movement produces a new `SpatialState`; presentation objects are never
the canonical location record.

## Distance and reach

The initial square-grid implementation exposes explicit distance metrics:

- `grid` — maximum horizontal/elevation cell-step distance;
- `manhattan` — orthogonal horizontal steps plus elevation;
- `euclidean` — three-dimensional center-to-center distance.

Placement distance uses the minimum distance between occupied footprint cells. Reach checks are then
simple comparisons against a caller-supplied reach value instead of being hidden in attack UI code.

## Movement authority

Movement is split into reusable operations:

- `step_is_legal()`;
- `step_cost()`;
- `validate_path()`;
- `find_path()`;
- `reachable_cells()`;
- `find_actor_path()`.

The default square-grid policy supports diagonal movement and prevents diagonal corner cutting
through blocked geometry. `MovementPolicy` makes this explicit and configurable for content/rulesets.

Movement legality checks:

- logical bounds;
- destination footprint occupancy;
- terrain collision;
- terrain movement-mode compatibility;
- diagonal/corner policy;
- walking elevation-step limits.

Movement cost incorporates logical cell size, elevation delta, and difficult-terrain multipliers.
Flying may ignore difficult-terrain cost by policy while still respecting logical collision and
movement-mode compatibility.

`ActorState` movement data is adapted directly through the existing v0.4 `MovementMode` and
`MovementSpeed` records. No second actor-speed model exists in the spatial package.

## Combat integration

`move_in_encounter()` is the narrow v0.5/v0.6 integration point:

```text
current EncounterState movement budget
        ↓
SpatialRuntime validates route and computes authoritative cost
        ↓
CombatRuntime.spend_movement(exact_spatial_cost)
        ↓
new SpatialState + new EncounterState
```

The spatial runtime does not duplicate current-turn validation, combat-condition restrictions, or
movement-budget mutation. The existing combat runtime still owns those checks.

Both runtimes are immutable/event-oriented, so a rejected movement operation leaves both input
states unchanged.

## Movement events and replay

Accepted spatial movement is represented as a versioned `SpatialEvent` with `schema_version: 1` and
`event_type: entity.moved`.

The event records:

- source and destination anchors;
- ordered logical path;
- authoritative cost in feet;
- movement mode;
- geometric threat-zone entries/exits.

`apply_spatial_event()` requires contiguous sequence numbers and revalidates the recorded path and
cost against the logical state before advancing position. Corrupt/stale event logs therefore fail
closed rather than silently relocating an entity.

Canonical JSON/JSONL serialization is defined in `spatial/serialization.py` and the public contract is
`schemas/v1/spatial-event.schema.json`.

`replay_spatial()` reconstructs the same spatial state from an initial state plus ordered events.

## Line of sight and cover

LOS uses deterministic logical grid traces, per-cell elevation, explicit obstacle height, and
optional blocking placements. Source/target footprints can provide multiple candidate rays; a target
is visible when at least one logical footprint ray is unobstructed.

Cover is explicit logical data, not inferred from rendered pixels. A fully blocked LOS result maps to
`total` cover. Otherwise the query returns the strongest explicit terrain/placement cover source
along the chosen logical ray.

This is intentionally a generic tactical classification layer. Rules that turn a cover class into a
numeric modifier remain rules-runtime/combat concerns.

## Areas of effect

The spatial package provides reusable geometry rather than named-spell cases:

- sphere;
- cube;
- cylinder;
- cone;
- line.

Each shape returns deterministic logical cell membership plus intersecting entity IDs. v0.8 spell
runtime can compose these generic shapes without introducing spell-name conditionals in Godot or the
spatial package.

## Threat inputs

`ThreatDefinition` and `path_threat_transitions()` calculate only geometric zone transitions.

For example, a path can report that an actor exited another entity's reach. This is an **input** to
reaction/opportunity logic; the spatial package does not decide whether a reaction exists, is legal,
or is spent. v0.5 combat/rules authority owns those decisions.

## Godot navigation adapter contract

`NavigationProposalProvider` and `NavigationPathProposal` define the rendering/navigation boundary.
A Godot adapter may propose a logical path based on `NavigationServer` or scene geometry, but
`validate_navigation_proposal()` checks:

- matching logical space ID;
- known entity ID;
- non-stale starting anchor;
- movement-mode legality;
- occupancy/collision;
- terrain/elevation;
- movement cost/budget.

The proposed path is therefore an optimization/input, never tactical authority.

## Read-only query surface

`SpatialQueryService` exposes transport-neutral, JSON-shaped query results suitable for the existing
client bridge or other tools:

- `spatial.occupancy`;
- `spatial.distance`;
- `spatial.reach`;
- `spatial.path`;
- `spatial.reachable`;
- `spatial.los`;
- `spatial.cover`;
- `spatial.area`;
- `spatial.movement_modes`;
- `spatial.threatened_cells`.

The live bridge host does not invent a default tactical map/spatial state. A campaign/session layer
must supply the relevant `SpatialState`/actor state before delegating those query names. This avoids
creating fake client-only spatial authority merely to make a preview endpoint respond.

## Determinism

v0.6 spatial queries use no randomness, wall clock, network, filesystem, or Godot API. Given the same
logical space, placements, actor movement data, policy, and query, the result is deterministic.

Pathfinding uses stable cell ordering for tie-breaking, and canonical spatial-event serialization uses
stable key ordering.

## Validation and adversarial behavior

The v0.6 tests cover:

- multi-cell occupancy and overlap rejection;
- explicit distance/reach metrics;
- collision routing and diagonal corner policy;
- difficult terrain and movement cost;
- elevation and movement-mode behavior;
- reachable-space budgets;
- LOS blockers and cover;
- elevation-aware visibility;
- generic area shapes;
- threat-zone transitions;
- Godot/navigation proposal validation;
- spatial event serialization and replay;
- bridge-ready read-only query shapes;
- v0.5 combat movement-budget integration;
- malformed grids, placements, events, shapes, queries, and navigation proposals.

The milestone's implementation is not considered fully exited until the exact PR head executes the
repository Ruff, strict Mypy, pytest/coverage, schema/governance, importer determinism, and Godot
checks successfully.

## v0.7 handoff

The Godot vertical slice can now consume v0.6 outputs rather than deciding legality itself:

- reachable-movement highlighting from `spatial.reachable`;
- path/cost preview from `spatial.path`;
- targeting reach from `spatial.reach`;
- LOS and cover overlays from `spatial.los` / `spatial.cover`;
- generic AoE overlays from `spatial.area`;
- Godot navigation paths validated through `NavigationPathProposal`.

The next integration work should bind campaign/encounter spatial state into the existing engine bridge
and client previews without moving any of these authoritative calculations into GDScript.
