# v1.0 Godot RPG client completion

## Scope

This phase completes the remaining implementation work in the active v1.0 playable-RPG and Godot-client backlogs while preserving the repository authority boundary: Godot presents engine facts and submits intent; Python owns gameplay legality, state transitions, randomness, tactical outcomes, and save validation.

The phase closes the client-facing gaps around:

- exploration context and action prompts;
- authoritative travel/rest availability and rejection reasons;
- two-way shop trade UX;
- engine-provided equipment compatibility choices;
- world-to-tactical encounter start/completion intents;
- explicit trap/environment interaction content;
- release credits/attribution presentation;
- deterministic release-source packaging;
- campaign completion acceptance across save/restore.

## Exploration shell

`world.actions` remains the authoritative source for the Adventure action column. The world bridge enriches its runtime results with presentation-safe descriptors rather than asking Godot to infer legality:

- `area_name` and `area_tags`;
- `exploration_prompt`;
- per-travel `available` and `reason`;
- per-interaction `available` and `reason`;
- `can_rest` and `rest_reason`;
- encounter `available`, `active`, and `reason`;
- shop item ownership, stock, buy/sell availability, and rejection reasons.

The Godot Adventure overlay renders these values directly. Disabled buttons and tooltips therefore explain authoritative rejection without reproducing world rules in GDScript.

## Shop and trade flow

The world runtime already owns `shop.buy` and `shop.sell`, stock, inventory ownership, buy/sell prices, and currency mutation. This phase completes the Godot surface by showing both Buy and Sell controls for every engine-returned shop item.

Godot does not calculate whether a transaction is legal. The bridge supplies `buy_available`, `buy_reason`, `sell_available`, `sell_reason`, `owned_quantity`, and stock. Button presses submit one-item typed intents through the existing world command path and reconcile only from accepted authoritative snapshots.

## Equipment compatibility

The previous UI accepted a free-form equipment-slot string because the engine did not expose compatibility data. v1.0 now defines `EquipmentCompatibility` as campaign/runtime data and advertises `inventory.equipment-options.v1`.

`inventory.equipment_options` returns:

- active party actor IDs;
- owned items for which equipment compatibility exists;
- legal slot IDs and presentation labels for each item.

The production Godot UI hides the old free-text field and uses an `OptionButton` populated from this query. The bridge independently validates every `inventory.equip` item/slot pair before allowing the world command through, so a modified client cannot bypass compatibility by sending an arbitrary slot.

A non-user-facing legacy fixture path remains while older headless tests are migrated; it cannot bypass the Python bridge validation boundary.

## Campaign content and completion

The original `Lanterns Below` fixture now explicitly demonstrates the root v1.0 content categories:

- village: Reedhollow Square and Market Row;
- wilderness route: Old Quarry Road;
- dungeon: Sunken Quarry Mouth, Flooded Underworks, and Lantern Vault;
- branching quest/dialogue: Warden Ilar plus the Surveyor's Echo choice;
- skill checks: collapsed marker, flooded gate, survey lantern;
- trap/environment interaction: suspended stonefall trigger;
- three regular encounter gates: Roadside Scavengers, Quarry Watchers, Underworks Swarm;
- boss gate: The Hollow Warden;
- four premade heroes seeded by the world bridge: Mira Quill, Aster Vale, Tovan Reed, and Sable Fen.

The existing world/tactical bridge owns `world.begin_encounter` and validates `world.complete_encounter` against a party tactical victory before recording world progression. The Adventure UI now distinguishes starting an available encounter from recording the result of an already-active tactical encounter.

## End-to-end acceptance

`tests/test_v1_completion.py` adds an executable headless campaign acceptance path. It exercises:

1. party/campaign start;
2. quest acceptance dialogue;
3. travel to the village shop;
4. buy, rest, and sell;
5. road travel and a deterministic skill interaction;
6. first encounter completion;
7. quarry travel, environment interaction, and second encounter;
8. underworks trap plus survey-lantern interaction;
9. the branching Surveyor's Echo decision;
10. world snapshot save/restore with RNG parity;
11. third encounter, boss-area travel, and boss completion;
12. final `flag:campaign-complete` state.

The same module also verifies campaign content counts, authoritative equipment choices, and authoritative exploration/trade descriptors.

`res://tests/world_rpg_completion_tests.gd` covers the presentation boundary with `FakeEngineTransport`: exploration text, disabled/reasoned actions, Sell routing, equipment dropdown IDs, encounter begin/completion intent, and credits presentation. It is registered in `scripts/local_ci.sh`.

## Credits and release packaging

The Adventure management tabs now include a Credits surface. The repository also contains `apps/godot-client/CREDITS.md` with the original-content boundary, SRD attribution expectations, Godot licensing note, and authority architecture credit.

`scripts/package_v1_release.py` creates a deterministic source release ZIP under `dist/` by default. It includes:

- the Godot project resources;
- `apps/godot-client/CREDITS.md`;
- root `README.md`;
- every tracked `LICENSES/` attribution file;
- `RELEASE-MANIFEST.json` with SHA-256 and byte length for every bundled source file.

The builder intentionally does not redistribute a Godot engine/editor binary. A downstream binary-export release must add the applicable Godot engine license notice for the binary it distributes.

`tests/test_release_packaging.py` builds the bundle twice and requires byte-for-byte deterministic output plus the required credits/attribution entries.

Build the source release bundle with:

```bash
python scripts/package_v1_release.py
```

## Validation status

All new executable tests are wired into the repository's local CI path. GitHub-hosted Actions for this repository have repeatedly terminated before producing job steps, so those hosted failures are infrastructure/pre-step failures rather than evidence that the Python or Godot suites failed.

Exact-head hosted validation and any explicitly manual interactive playthrough remain separate acceptance evidence; implementation checkboxes should not be conflated with those runner/manual gates.
