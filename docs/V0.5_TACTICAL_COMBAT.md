# v0.5 Tactical Combat

v0.5 adds a deterministic, headless tactical-combat layer on top of the merged v0.3 rules runtime and v0.4 shared actor model.

## Ownership boundary

The combat package owns:

- encounter lifecycle;
- deterministic initiative ordering;
- round and turn progression;
- action, bonus-action, reaction, and movement-budget accounting;
- abstract attack resolution against actor defense state;
- generic damage/healing and temporary-hit-point handling;
- resistance, immunity, and vulnerability hooks keyed by data-driven damage-type IDs;
- explicit reaction windows;
- combat-condition restrictions;
- licensed zero-hit-point/death-state behavior represented as explicit policy;
- versioned combat events and deterministic replay.

It does **not** own:

- Godot presentation or scene-tree state;
- route/path validation;
- logical occupancy;
- range/reach geometry;
- terrain/elevation;
- line of sight;
- cover;
- areas of effect.

Those spatial-authority concerns remain v0.6. A caller may spend movement budget in v0.5 only after whatever later spatial adapter determines that the requested movement is legal.

## Core flow

```text
combat command
      ↓
validation
      ↓
deterministic resolution
      ↓
CombatEvent(s)
      ↓
pure combat reducer
      ↓
EncounterState
```

`CombatRuntime` does not directly mutate an `EncounterState`. Commands emit ordered events and `apply_combat_event()` produces the next immutable state.

## Shared actors

v0.5 consumes the v0.4 `ActorState` directly. It does not introduce a second combatant/character representation.

`CombatantState` wraps an actor only with encounter-specific state:

- defense adjustments;
- life/zero-hit-point policy;
- death-save track where applicable;
- per-turn action economy;
- encounter-local combat metadata.

Persistent character identity, abilities, HP record, AC, movement modes, inventory, resources, and conditions remain owned by `ActorState`.

## Initiative

Initiative uses the existing v0.3 D20/RNG abstraction with Dexterity. The runtime never calls an ad-hoc random API.

For deterministic replay, exact ties use the project-defined stable order:

1. higher initiative total;
2. higher Dexterity modifier;
3. lexical actor ID.

The third rule is a deterministic engine policy so identical input always produces identical ordering. It is not intended to replace table-specific tie choices in higher-level content or UI policy.

## Action economy

At the start of a combatant's turn, v0.5 refreshes encounter capacity for:

- one action;
- at most one bonus-action slot;
- reaction availability;
- walking movement budget.

`bonus_action_available` means the slot is unspent. It does **not** mean every actor automatically has a legal bonus-action option. Feature/action definitions must still establish whether a specific bonus action is permitted.

Reactions are spent only through an explicit `ReactionWindow`; this keeps trigger eligibility visible and replayable.

## Movement accounting

`spend_movement()` subtracts feet from the current turn's movement budget. It intentionally does not answer whether a path exists or is legal.

That separation is required so v0.6 can add occupancy, movement cost, terrain, elevation, LOS, cover, and path legality without replacing combat turn state.

## Attacks

`AttackDefinition` is intentionally abstract and data-driven. It contains:

- stable attack ID;
- governing ability;
- proficiency rank;
- damage dice;
- generic damage-type ID;
- optional numeric bonus;
- action-resource cost.

There are no named-item, named-spell, or named-creature conditionals in the combat engine.

Attack D20 generation reuses v0.3 `RulesRuntime.resolve_d20()`. v0.5 supplies the tactical success semantics against target armor class, including attack-roll natural-1/natural-20 behavior and critical damage-dice handling required by the supported licensed rules.

## Damage and healing

`DamagePacket` contains only an amount and generic damage-type ID. `DefenseProfile` supplies resistance, immunity, and vulnerability sets.

The generic defense pipeline applies:

1. immunity;
2. resistance;
3. vulnerability.

Temporary hit points are consumed before current hit points. New temporary hit points do not silently stack: `TemporaryHitPointChoice` explicitly records whether the existing or newly offered value is retained.

Ordinary healing is capped by maximum HP and can return an eligible zero-HP character to conscious state. Restoring a dead combatant is intentionally outside this generic healing operation.

## Zero-HP policy

`ZeroHitPointRule` makes the supported licensed distinction explicit rather than inferring it from names:

- `CHARACTER` supports unconscious/stable/dead transitions and death saves;
- `MONSTER` uses the simpler default zero-HP end state.

Actor kind supplies the default (`CREATURE` → monster policy; hero/NPC → character policy), but callers can override it per encounter when licensed/content rules require a different policy.

The runtime also records the supported massive-damage and death-save transitions as events. The implementation remains data/state oriented and does not add graphic presentation detail.

## Combat conditions

Conditions remain the v0.3/v0.4 `ConditionInstance` data. `CombatConditionRule` adds encounter-local restrictions such as blocking:

- action use;
- bonus-action use;
- reactions;
- movement spending.

This avoids special-casing named conditions inside command handlers.

## Events and replay

Combat events use `schema_version: 1` and `schemas/v1/combat-event.schema.json`.

Events carry contiguous sequence numbers and canonical payloads. `serialize_log()` emits deterministic JSONL. `replay_combat()` reconstructs encounter state from the same preparing state plus ordered events.

Representative event families include:

- `initiative.rolled`;
- `encounter.started` / `encounter.ended`;
- `turn.started`;
- `action.spent`;
- `movement.spent`;
- `reaction.window.opened` / `reaction.window.closed`;
- `attack.resolved`;
- `damage.applied`;
- `healing.applied`;
- `temporary_hp.changed`;
- `condition.applied` / `condition.removed`;
- `death_save.resolved`.

## Determinism

All random combat outcomes use the repository's versioned deterministic RNG and dice abstractions. Tests use real `DeterministicRNG.from_seed(...)` seeds, including edge cases for attack rolls and death saves.

Given the same actors, encounter configuration, RNG seed, and commands, combat resolution and canonical event logs are reproducible.

## Validation

The v0.5 test suite covers:

- deterministic initiative and stable tie ordering;
- action/bonus-action/reaction/movement accounting;
- combat-condition restrictions;
- reaction-window eligibility and refresh;
- attack success/critical edge cases;
- defense adjustment ordering;
- temporary HP behavior;
- character/monster zero-HP policies;
- healing and death-save state changes;
- malformed encounter, event, attack, damage, and command inputs;
- event JSON/JSONL round trips;
- event-sequence rejection;
- live-state versus replay parity.

The focused local suite reached 29 passing tests and 96% branch-aware coverage for `godot_dnd_engine.combat`.

## v0.6 handoff

v0.6 Spatial Authority should consume the active actor/encounter state and add authoritative answers for:

- occupancy;
- distance/reach;
- movement cost and path legality;
- terrain/elevation;
- LOS/visibility;
- cover;
- AoE/shape queries;
- movement-mode adapters.

It should feed legality into v0.5 commands rather than duplicating turn order, action economy, attack, damage, or life-state logic.
