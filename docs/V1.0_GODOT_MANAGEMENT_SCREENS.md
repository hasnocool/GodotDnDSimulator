# v1.0 Godot Campaign Management Screens

## Scope

This phase advances the v1.0 RPG client shell from the initial Adventure action list into dedicated campaign-management surfaces while preserving the authoritative-engine boundary.

The Godot client now presents four management tabs inside the Adventure overlay:

- Journal — quest statuses and ordered journal entries from `world.journal`;
- Map — current area, visited state, and area exits from `world.map`;
- Party — active authoritative party IDs and equipped-item assignments from `world.party`;
- Inventory — currency, party inventory counts, and equipped items from the isolated world snapshot.

## Authority boundary

These screens are read-only presentations of engine-returned data. Godot does not infer visited state, quest progress, inventory ownership, equipment ownership, currency, or travel connectivity.

The world snapshot remains isolated from the tactical/core `AuthoritativeMirror`; the Adventure view stores its own copied world snapshot and renders management data from world-specific query responses.

## Refresh model

Opening or refreshing the Adventure overlay requests:

- `world.snapshot`;
- `world.actions`;
- `world.journal`;
- `world.map`;
- `world.party`.

After accepted world commands, the view refreshes those queries so management screens reconcile to authoritative state rather than optimistic local mutations.

## Testing

`res://tests/world_rpg_tests.gd` verifies that:

- the new world queries are issued through the bridge;
- map rows render only from `world.map` responses;
- party/equipment rows render only from `world.party` responses;
- inventory and currency render from the isolated authoritative world snapshot;
- journal/quest content renders from `world.journal`;
- world state still does not replace the tactical/core authoritative mirror.

## Follow-up phases

The next v1.0 client slices should build on these surfaces rather than bypass them:

1. richer party cards using authoritative character-record queries;
2. interactive inventory/equipment actions through `inventory.*` commands;
3. production save/load UX using the existing `world.save-replay.v1` capability with non-blocking persistence;
4. map navigation/area-selection UX without making the visual map authoritative;
5. campaign-completion and save/restore headless Godot acceptance coverage.
