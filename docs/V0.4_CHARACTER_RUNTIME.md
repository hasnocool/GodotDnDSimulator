# v0.4 Character Runtime

## Purpose

v0.4 introduces the first rich, shared actor model for heroes, NPCs, and creatures. It builds on the deterministic v0.3 rules runtime rather than replacing it. Godot remains presentation-only.

The owning package is `engine/src/godot_dnd_engine/actors/`.

## Architecture

```text
ActorState
  identity / kind / size / level
  six ability scores
  proficiency bonus
  HP / temporary HP / AC
  skills / saves / generic proficiencies
  movement modes / senses
  inventory / equipment assignments
  resources / conditions
  selected character options / tags
        |
        v
RuleSubjectState adapter
        |
        v
v0.3 requirements / targets / effects / conditions / resources
```

`ActorState` is immutable. The v0.3 rules layer remains the generic authority for resources, conditions, targeting, and effect application. Actor adapters project actors into `RuleWorldState`, apply the existing effect pipeline, then merge the resulting rule state back into actors.

## Shared actor model

`ActorKind` supports `hero`, `npc`, and `creature` without separate incompatible state classes.

The actor state includes:

- all six ability scores exactly once;
- explicit proficiency bonus and optional level;
- current, maximum, and temporary hit points;
- armor class as defense state;
- SRD skill proficiencies and saving-throw proficiencies;
- generic training/equipment/tool proficiency identifiers;
- walk, climb, swim, fly, and burrow speed records;
- generic named senses with optional ranges;
- inventory entries plus equipment-slot assignments;
- v0.3 `ResourcePool` and `ConditionInstance` values;
- selected character-option IDs and generic tags.

The SRD 5.2.1 skill list and default skill-to-ability mappings are represented as structured data. Combat attack success, damage/healing, incapacitation/death, resistance/immunity, and action economy are intentionally not implemented here; those belong to v0.5.

## Rule runtime integration

Actors expose a `RuleSubjectState` projection. `actors_to_rule_world()` and `merge_rule_world()` preserve the richer actor fields while allowing v0.3 rule effects to update resources and conditions deterministically.

`apply_actor_effects()` is the convenience bridge for applying an ordered v0.3 `RuleEffect` batch to actors. It does not introduce a second effect implementation.

## Character options and constraints

`CharacterOption` and `ChoiceGroup` provide a data-driven initial choice model:

- stable option IDs and categories;
- minimum/maximum group cardinality;
- option requirements;
- conflicts;
- granted actor tags.

The runtime rejects duplicate option IDs, unknown references, invalid group cardinality, unsatisfied requirements, conflicting selections, and unknown requested choices.

This is intentionally headless. v0.9 will provide the full player-facing character-creator workflow and source its choices from engine/content APIs rather than hardcoded UI lists.

## Headless creation API

`CharacterCreationSpec` defines validated base actor state plus available options and choice groups. `CharacterCreationRequest` contains the requested actor identity and selected option IDs. `create_character()` validates the request and returns a deterministic `CharacterCreationResult` containing the immutable actor.

Character creation currently builds a complete starting actor state; it does not mutate campaign state or emit campaign events yet.

## Serialization and migration

Actor payloads use `schema_version: 1` and have a repository JSON Schema at `schemas/v1/actor.schema.json`.

The serializer:

- writes canonical sorted JSON;
- preserves abilities, HP/defense, proficiencies, movement, senses, inventory/equipment, resources, conditions, options, and tags;
- rejects malformed field shapes and unknown schema versions;
- includes an explicit migration path from the earlier proof-of-concept actor payload shape (`schema_version: 0`) to v1.

Any future incompatible actor format must add a migration rather than silently changing existing saves/content.

## Determinism and validation

Collections whose order should not affect meaning are sorted into canonical order when actor state is constructed. Duplicate IDs/modes/skills/senses/equipment slots are rejected where uniqueness is required.

No random behavior, wall-clock access, filesystem/network I/O, database access, or Godot dependency is introduced by this package.

## Test coverage

The v0.4 focused suite covers:

- hero/NPC/creature state sharing;
- skill/save/generic proficiency calculations;
- movement and senses;
- inventory/equipment reference integrity;
- HP/temporary-HP/AC validation;
- actor-to-rule-world round trips;
- v0.3 effect application through actor adapters;
- option cardinality, requirements, conflicts, and unknown choices;
- headless character creation;
- deterministic serialization round trips;
- v0-to-v1 migration;
- malformed actor data and duplicate-state rejection.

The local phase candidate passed 46 focused tests with 96% coverage of `godot_dnd_engine.actors` before publishing the branch.

## v0.5 handoff

v0.5 Tactical Combat should consume `ActorState` rather than invent another combatant model. It should add encounter lifecycle, initiative/turns, action economy, attack resolution, damage/healing, defenses/resistances, reaction windows, combat conditions, and supported incapacitation/death behavior through deterministic commands/events/reducers.

v0.6 remains responsible for spatial authority such as occupancy, distance, path legality, terrain, LOS, cover, and AoE geometry.
