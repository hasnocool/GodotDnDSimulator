# v0.3 Rules Runtime

## Status

This document describes the executable headless rules runtime introduced in v0.3. The runtime extends the deterministic foundation from v0.1 and consumes mechanically structured data compatible with the canonical/provenance contracts introduced in v0.2.

It does not make Godot authoritative, does not depend on the rules-import tooling at runtime, and does not attempt to model the full actor/character state planned for v0.4.

## Boundary

The authoritative direction remains:

```text
canonical/imported rule data
          ↓
     RulesRuntime
          ↓
validation / resolution / effects
          ↓
typed outcomes + immutable rule-state transforms
          ↓
engine commands/events/reducers
          ↓
Godot presentation
```

`engine/src/godot_dnd_engine/rules/` is pure Python and has no Godot, network, filesystem, database, or wall-clock dependency.

## D20 primitives

The runtime provides:

- six typed abilities;
- validated ability scores from 1 through 30;
- the standard ability-modifier formula `(score - 10) // 2`;
- level 1–20 character proficiency-bonus progression;
- none, half, full, and double proficiency ranks;
- ability-check, saving-throw, and attack-roll D20 test kinds;
- typed difficulty classes;
- normal, advantage, and disadvantage roll modes.

Advantage/disadvantage uses the project RNG and existing deterministic dice service. Multiple sources of the same mode do not create additional dice. When at least one advantage source and at least one disadvantage source are present, the result is a normal single-D20 roll.

A test succeeds when the final resolved total meets or exceeds its difficulty class. Attack-roll AC integration remains a v0.5 combat concern; the generic D20 API already supports attack-roll contexts without embedding combat state here.

## Resolution context and outcome

`ResolutionContext` identifies the requested test with:

- context ID;
- D20 test kind;
- actor ID;
- governing ability;
- proficiency rank;
- optional difficulty class;
- optional target ID;
- reason/audit label;
- rule tags.

`D20Outcome` records:

- resolved roll mode;
- every raw D20 rolled;
- selected D20;
- ability modifier;
- proficiency modifier;
- complete modifier-pipeline resolution;
- final total;
- optional success/failure;
- RNG algorithm identity.

The outcome is deterministic for the same RNG state and inputs.

## Modifier pipeline

Rules do not special-case named spells/items/features. `RuleModifier` provides reusable operations:

```text
set
add
minimum
maximum
```

Modifiers have deterministic integer priority, optional source identity, and optional stacking groups.

Supported stacking policies are:

```text
stack     apply every modifier in the group
highest   keep the numerically highest value
lowest    keep the numerically lowest value
replace   keep the highest-priority modifier, then stable ID as tie-breaker
```

A stacking group must use one policy consistently. Mixed policies fail validation rather than producing order-dependent behavior.

After group selection, operations are applied deterministically using priority, operation order, and stable modifier ID. The resolution records both applied and suppressed modifiers for debugging and UI explanation.

These stacking policies are project runtime primitives; imported mechanics must explicitly choose the semantics they require rather than inferring them from prose at runtime.

## Resources and costs

`ResourcePool` is an immutable bounded integer resource. `ResourceCost` represents a requested spend.

`spend_costs()` aggregates repeated costs by resource ID before applying them. It returns a new subject state and a canonical list of amounts spent.

If any cost is invalid, missing, or exceeds resource bounds, resolution fails and the caller retains the original immutable state. Partial spending is not committed.

## Lightweight pre-v0.4 rule state

v0.3 deliberately does not introduce the full hero/NPC/creature actor model. Instead, generic rules operate on:

- `RuleSubjectState` — subject ID, tags, resource pools, and conditions;
- `RuleWorldState` — deterministic sorted collection of subjects.

v0.4 should adapt its richer actor model to these primitives or evolve them through a documented compatibility change rather than duplicating rule behavior.

## Requirements

`Requirement` supports reusable predicates for:

- required tag;
- absent tag;
- minimum resource value;
- present condition;
- absent condition;
- ruleset capability.

Evaluation returns an explicit `RequirementResult` listing failed requirement IDs. It does not throw merely because a legal requirement is not satisfied; malformed requirements still fail validation.

## Target selectors

`TargetSelector` is presentation-independent. It supports:

```text
self
single
all
```

Selectors can require/exclude tags and impose a maximum target count. Selection order is deterministic because authoritative world subjects are stably sorted.

Spatial range, line of sight, cover, path legality, area shapes, and elevation remain v0.6 spatial-authority concerns. They should extend target legality rather than moving target authority into Godot.

## Effects

`RuleEffect` currently provides generic primitives for:

- resource deltas;
- condition application;
- condition removal.

Effects are applied as an ordered pure transform over immutable state. The input world is never mutated, so a failing multi-effect batch cannot partially modify caller state.

Each effect has a stable effect ID and a target selector. Duplicate IDs in one batch are rejected.

Later milestones can extend the effect kind set for damage, healing, movement, attacks, spell resolution, inventory changes, and other mechanics without creating named-rule conditionals.

## Conditions and duration

Conditions carry:

- condition ID;
- optional source ID;
- optional duration;
- stack count.

Durations support ticks, turns, rounds, or permanent duration. `advance_condition_durations()` advances only conditions matching the requested unit and removes expired conditions deterministically.

Condition application supports:

```text
unique   existing condition is retained
refresh  existing instances are replaced with the new instance/duration
stack    a new instance is added
```

The specific imported rule decides which generic policy is correct.

## Triggers and reactions

`Trigger` matches a typed event name and optional required event tags.

`ReactionHook` combines:

- stable hook ID;
- owner/subject ID;
- trigger;
- requirements;
- effects reserved for reaction execution;
- deterministic priority.

`collect_reactions()` returns legal matches sorted by priority and hook ID. It identifies reaction opportunities but does not silently execute them; the engine can later open a reaction window, ask an AI/player, or auto-resolve a rule that explicitly permits it.

## Ruleset capabilities

`RulesetCapabilities` allows a rules/content pack to declare which runtime families it can execute. The initial v0.3 SRD-oriented capability set includes:

- D20 tests;
- advantage/disadvantage;
- modifier pipeline;
- resources;
- requirements;
- target selectors;
- effects;
- durations;
- conditions;
- reactions.

Runtime entry points fail closed when a required capability is absent.

## Importer/runtime conformance

The v0.3 test suite includes canonical importer-shaped `CanonicalEntity` fixtures carrying v0.2 provenance and a structured `mechanics` map. Tests translate those mechanical fields into v0.3 contexts and confirm deterministic resolution.

This is deliberately not free-form prose interpretation. The production importer currently emits data-only entities until audited mechanical compilation is added. Full official-SRD mechanical coverage remains dependent on the outstanding v0.2 full-source audit.

## Determinism

All random D20 draws use the existing `pcg32-v1` `DeterministicRNG` through `roll_expression()`. The rules package never calls global random APIs.

Pure transforms use stable ordering for subjects, modifiers, targets, effects, and reactions. Inputs are immutable dataclasses wherever practical.

The v0.3 local package suite covers:

- official D20 modifier/proficiency behavior;
- advantage/disadvantage and cancellation;
- deterministic repeated resolution;
- save/DC resolution;
- modifier operation and stacking order;
- atomic resource spending;
- target filtering/order;

Ruff, Mypy, the complete repository pytest/coverage suite, governance checks, importer determinism, and Godot validation remain repository CI gates.

## v0.4 handoff

The next character-runtime milestone should build the durable shared actor model and connect it to these primitives:

```text
Actor
 ├─ ability scores
 ├─ proficiencies
 ├─ HP / temp HP / defenses
 ├─ speeds / senses
 ├─ inventory / equipment
 ├─ resources
 ├─ conditions / effects
 └─ rule tags / capabilities
       ↓
RulesRuntime
```

v0.4 should not duplicate D20, modifier, resource, condition, target, or reaction logic already established here.
