# v1.0 Playable RPG

## Goal

v1.0 adds the first campaign/world layer around the already merged rules, character, combat, spatial, spell, and character-creator systems. The new layer is authoritative Python code; Godot remains presentation, input, and local file UX.

The implementation in this phase is the production architecture for a small original adventure, **Lanterns Below**. It provides the campaign state machine and client shell needed to connect exploration and narrative state to existing tactical play without moving rules decisions into GDScript.

## Authority split

```text
Godot Adventure UI
    |
    | world/dialogue/shop/inventory intent
    v
WorldClientBridgeSession
    |
    +--> CharacterCreatorService
    +--> SpellEnabledTacticalSession
    +--> WorldRuntime
             |
             +--> deterministic RNG
             +--> versioned world events
             +--> immutable WorldState replacement
             +--> validated save/restore
```

Godot may render world state, gather party IDs, choose dialogue/action IDs returned by the engine, and persist a world snapshot to a local file. Godot does not decide travel legality, dialogue availability, skill outcomes, prices, inventory mutation, quest state, encounter prerequisites, or whether a tactical victory is complete.

## Separate authoritative streams

The tactical bridge already owns the normal bridge `snapshot`/`events` channel. v1.0 deliberately does **not** put world snapshots in those fields.

World responses use:

- `world_snapshot`
- `world_events`
- `presentation_events`

This prevents `EngineBridge._ingest_authoritative_payload()` from replacing the tactical/core `AuthoritativeMirror` with exploration state. `WorldRPGView` maintains a separate presentation copy of the world snapshot and a separate world sequence.

## World state

`WorldState` tracks:

- world sequence;
- current area;
- party actor IDs;
- persistent flags;
- quest statuses;
- party inventory quantities;
- equipment assignments;
- currency;
- active dialogue/node;
- completed encounters;
- journal entries;
- rest count.

The state is immutable. Commands emit ordered `WorldEvent` records and `apply_world_event()` returns a new state.

## Commands

The current world command families are:

- `world.start`
- `world.travel`
- `world.resolve_interaction`
- `world.rest`
- `world.complete_encounter`
- `world.load`
- `dialogue.start`
- `dialogue.choose`
- `shop.buy`
- `shop.sell`
- `inventory.equip`

All commands use the existing typed command envelope and optimistic `expected_sequence` check.

### Skill/obstacle checks

`world.resolve_interaction` never trusts a client-supplied modifier. `WorldClientBridgeSession` selects the requested/primary party actor, looks up the actor in the authoritative creator service when available, resolves the interaction's declared ability to the existing `Ability` enum, and injects the actor's authoritative ability modifier before the world runtime rolls d20 using `pcg32-v1`.

The resulting world event records raw roll, bonus, total, DC, success, effects, and `rng_after`.

### Tactical encounter handoff

A world encounter cannot be marked complete merely because the client asks. `WorldClientBridgeSession` requires the current `SpellEnabledTacticalSession` encounter status to be `ended` before accepting `world.complete_encounter`.

After recording a world victory, the bridge creates a fresh deterministic tactical session for the next encounter gate. The current v1.0 adventure reuses the existing tactical vertical-slice encounter template as the combat handoff implementation; authored per-gate encounter templates remain part of the v1.0 completion backlog rather than being faked in the world layer.

## Queries

The client-facing world query surface includes:

- `world.snapshot`
- `world.save`
- `world.actions`
- `world.map`
- `world.journal`
- `world.party`
- `dialogue.current`
- `shop.inventory`

`world.actions` is the primary UI descriptor. It returns legal travel destinations, available interactions, encounter gates, shops, rest availability, dialogue descriptors, and premade party IDs. The Godot Adventure overlay builds buttons from those returned IDs/descriptors rather than owning content lists.

## Save/load and replay

World snapshots are versioned and contain:

- schema version;
- complete world state;
- deterministic RNG checkpoint;
- ordered world-event history.

`restore_world_runtime()` validates:

- schema version;
- campaign identity;
- RNG algorithm/state;
- area and quest references;
- collection/value types;
- active dialogue shape;
- event shape;
- event-tail sequence against snapshot state.

The restored runtime resumes from the exact RNG state. Godot may save/load the JSON-shaped snapshot locally, but the server validates a loaded snapshot before replacing authoritative world state.

## Godot Adventure shell

`WorldRPGView` is a capability-gated overlay launched from `AppShell` when the bridge advertises `world.runtime.v1`.

It renders engine-returned:

- area name;
- travel actions;
- dialogue actions and choices;
- skill interactions;
- encounter gates;
- shop items;
- journal/quest state;
- rest action;
- world sequence/currency.

It submits typed commands and keeps a separate world snapshot. It does not locally mutate the tactical mirror or world authority.

## Known completion gates

The v1.0 architecture is implemented, but the milestone is not considered fully proven until executable gates run successfully and the original campaign is completed end-to-end through Godot. In particular:

- the current environment still cannot perform a local Git checkout from GitHub;
- GitHub Actions runner behavior must be verified on the PR head;
- authored per-world-encounter tactical templates should replace the reused tactical proxy before claiming the final campaign encounter-content exit criterion;
- production packaging/attribution remains an explicit release gate.
