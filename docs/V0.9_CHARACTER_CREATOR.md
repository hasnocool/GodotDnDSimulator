# v0.9 Complete Character Creator

v0.9 adds a rules-driven character creation and advancement service on top of the existing v0.4 actor model and v0.8 spell/content contracts. The authoritative Python engine owns character legality; Godot renders the steps/options returned by the engine and submits typed intent.

## Authority boundary

Python owns:

- available creation steps and choice groups;
- species/background/class/skill/proficiency/equipment/spell/feature choices;
- requirements, conflicts, group cardinality, and unlock levels;
- ability-score assignment policy and final bonuses;
- starting HP, AC, movement, saves, proficiencies, inventory, equipment, tags, spells, and features;
- validation/review and final actor construction;
- created-character identity uniqueness within the creator session;
- level-up choice availability, proficiency progression, HP growth, and selected advancement effects.

Godot owns:

- step navigation and form presentation;
- local text entry for identity, appearance hooks, biography, and personality;
- visual selection state for engine-provided choice IDs;
- submission of preview/create/level-up intent;
- presentation of engine validation or the returned character record.

Godot does not hardcode species, backgrounds, classes, skills, equipment, spells, features, advancement legality, or ability-score rules.

## Engine package

`engine/src/godot_dnd_engine/character_creator/` contains:

- `model.py` — immutable creator catalog, choice/group, ability policy, draft, profile, and record contracts;
- `runtime.py` — authoritative creation preview, finalization, and level-up resolution;
- `service.py` — JSON-shaped query/command surface plus in-session created-record storage;
- `data.py` — catalog serialization/deserialization boundary for canonical/content-pack data;
- `catalog.py` — original non-SRD demo content used for v0.9 tests and local development.

The final rules-facing object remains the existing v0.4 `ActorState`. Appearance, biography/personality, and selected spell/feature IDs live in `CharacterRecord` so the actor schema is not silently broken by presentation/profile concerns.

## Character creation flow

The engine advertises these logical steps:

1. identity;
2. species;
3. background;
4. class;
5. ability scores;
6. skills/proficiencies;
7. starting equipment;
8. spells/features;
9. appearance hooks;
10. biography/personality;
11. review/validation.

`characters.creator.schema` returns the ordered steps, group cardinality, choice rows, ability policies, and profile-field hints. The UI may make those controls convenient, but `characters.creator.preview` is the authority that decides whether the draft is legal.

`characters.create` validates the same draft again and returns a versioned character record. Validation is not trusted merely because a preview was previously legal.

## Data-driven catalogs

`catalog_from_data()` and `catalog_to_data()` define the content boundary. A catalog can be supplied from audited generated SRD data, an original content pack, or another validated source without changing the creator runtime or Godot scene.

The v0.9 repository includes `catalog:original-v0.9-demo` only as original test/development content. It must not be mistaken for a complete SRD character-option dataset.

## Level-up flow

`characters.levelup.choices` asks the engine for choices unlocked at the actor's next supported level and filters them against existing selected options/requirements.

`characters.level_up` revalidates the selected advancement choices, advances the shared `ActorState` level/proficiency bonus and HP maximum, and records newly granted tags/spell IDs/feature IDs.

This is intentionally a generic advancement boundary. Future canonical class progression can add richer level-specific choice groups without moving advancement rules into Godot.

## Bridge capabilities

v0.9 adds:

- `characters.creator.v1`;
- `characters.creator.commands.v1`;
- `characters.levelup.v1`.

The default `godot-dnd-client-bridge` now uses `godot_dnd_engine.character_bridge:main`. The tactical/spell providers remain available by default. `--core-only` disables tactical/spell providers but intentionally retains character-creator services so creator testing is possible without a battle session.

## Godot client

`res://scenes/character_creator/character_creator.tscn` is a shell-owned overlay. `creator_launcher.gd` exposes it only when the negotiated bridge advertises `characters.creator.v1`.

The creator scene:

- builds choice controls from `characters.creator.schema`;
- assigns ability values from an engine-provided ability policy;
- stores only choice IDs and profile text locally;
- requests authoritative review validation;
- enables final creation only after a legal preview;
- submits `characters.create` rather than constructing an actor locally;
- can request and submit level-up choices after a character is created.

## Serialized character record

`schemas/v1/character-record.schema.json` covers the creator/profile wrapper. Its nested `actor` payload remains the existing v1 actor representation generated by `actor_to_dict()`.

## Tests

Python coverage includes:

- engine-generated step/choice schema;
- catalog external-data roundtrip;
- ability-policy enforcement and choice-group validation;
- creation into the shared actor model;
- profile/spell/feature retention;
- record storage and duplicate actor IDs;
- level-up choice filtering and transition;
- bridge capability/query/command behavior;
- character-record JSON Schema conformance.

Godot coverage in `res://tests/character_creator_tests.gd` proves that:

- the launcher is capability-gated;
- the creator asks the engine for its schema;
- rendered selections use returned choice IDs;
- the review step requests authoritative validation;
- no create command is sent before a legal preview;
- final creation uses the typed `characters.create` command.

## Validation and exit gate

The implementation checklist may be complete before the milestone exit criterion is proven. v0.9 is only fully validated after the exact integrated head passes Ruff, strict Mypy, full pytest/coverage, governance/schema/importer checks, Godot project parsing, and all headless Godot suites including the creator flow.

The full roadmap exit criterion additionally requires the supported production catalog to come from audited canonical rules/content data, not only the original demo fixture.

## v1.0 handoff

v1.0 can consume `CharacterRecord` objects for party creation/load and reuse the same creator overlay from a campaign/party shell. The creator should not grow exploration, dialogue, quest, shop, travel, or campaign-state responsibilities; those belong to the playable RPG milestone.
