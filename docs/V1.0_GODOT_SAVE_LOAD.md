# v1.0 Godot production save/load UX

## Scope

This v1.0 client phase adds production manual save/load UX to the Godot Adventure view without moving campaign authority or save validation into GDScript.

The feature provides:

- three local manual save slots;
- engine-produced lossless world-snapshot JSON;
- threaded local persistence under `user://`;
- a versioned Godot save envelope around the opaque engine-owned snapshot string;
- engine-validated `world.load` before any loaded state is presented as authoritative;
- user-visible slot metadata, errors, busy state, disconnect recovery, and backup recovery.

Autosaves, cloud synchronization, cross-device export/import, and broad save migration tooling remain separately scoped follow-up work.

## Authority boundary

```text
Save Game
   |
   v
Godot Save/Load panel
   |
   | query: world.save {encoding: "lossless-json"}
   v
Authoritative Python world runtime
   |
   | canonical world_snapshot_json + safe metadata
   v
WorldSaveStore worker thread
   |
   v
user://saves/world/slot-N.json

Load Game
   |
   v
WorldSaveStore worker thread
   |
   | persisted world_snapshot_json (opaque string)
   v
Godot Save/Load panel
   |
   | command: world.load + current expected_sequence
   v
Authoritative Python world runtime
   |
   | JSON decode + schema/campaign/RNG/references/events/sequence validation
   v
accepted structured world_snapshot
   |
   v
Adventure presentation reconciles
```

Godot never applies a snapshot merely because a local file parsed successfully. The local file is untrusted input. `world.load` remains the authoritative validation and replacement boundary.

## Why the snapshot is stored as text

The TCP bridge is JSON. Large deterministic RNG checkpoint integers can exceed the exact integer range of intermediary JSON-number representations used by presentation runtimes. Godot therefore must not parse, rewrite, or re-serialize authoritative snapshot numeric fields when persisting a save.

For the production persistence flow, `world.save` accepts `{"encoding": "lossless-json"}` and returns:

- `world_snapshot_json`: canonical JSON produced by Python, containing exact authoritative integer digits;
- `save_metadata`: small presentation-safe fields used for slot labels.

Godot stores `world_snapshot_json` as a JSON string inside its client-owned envelope and returns the exact string in the `world.load` command. Python performs the actual snapshot JSON parse and authoritative restore. The older structured `world.save`/`world.load` path remains supported for existing engine/tool callers, but the production Godot disk path intentionally uses the lossless representation.

## Local envelope v1

The client stores a small wrapper around the engine-owned snapshot string:

```json
{
  "format": "godot-dnd-world-save",
  "format_version": 1,
  "slot_id": "slot-1",
  "metadata": {
    "saved_at": "2026-08-22 18:00:00",
    "campaign_id": "campaign:local-dev",
    "sequence": 12,
    "area_id": "area:old-road",
    "area_name": "Old Quarry Road"
  },
  "world_snapshot_json": "{...canonical engine JSON...}"
}
```

`schemas/v1/godot-world-save-envelope.schema.json` versions this client-owned wrapper. The nested serialized snapshot remains deliberately opaque to the client schema because its semantics, compatibility, RNG representation, and validation remain owned by the Python world runtime.

Changing the envelope semantics requires a new `format_version` or an explicit migration. Existing versions must not be silently reinterpreted.

## Slot, size, and path safety

The production UI exposes only these fixed IDs:

- `slot-1`;
- `slot-2`;
- `slot-3`.

The store never derives a path from arbitrary player text. This prevents save-slot path traversal and keeps filenames stable for future migrations.

Save files are bounded to **1 MiB**, aligned with the current local bridge message limit so the client cannot accept a local save that it could never submit back to the engine. Unsupported envelope versions, malformed JSON, mismatched slot IDs, invalid top-level types, and missing/empty snapshot strings fail closed with a user-facing error.

## Non-blocking disk I/O

`WorldSaveStore` performs directory creation, envelope JSON encoding/decoding, file reads, file writes, and replacement work on a low-priority Godot `Thread` rather than the frame-critical main thread.

Only one save-store operation may run at a time. Worker completion is marshalled back to the main thread. The completion path checks whether the worker is still alive and, when necessary, retries on the next `SceneTree.process_frame` before joining the already-finished thread. Scene-tree/UI access remains on the main thread and the main thread never waits for live disk work.

The store uses a replacement flow:

1. encode and size-check the envelope;
2. write `slot-N.json.tmp`;
3. flush and verify the write;
4. move an existing final file to `slot-N.json.bak`;
5. rename the temporary file to the final slot path;
6. remove the backup after successful replacement.

If a final save is missing but its backup remains, reads can recover the backup and expose that fact in slot metadata.

## Save flow

`WorldSavePanel` does not serialize its cached `_world_snapshot` when the player presses Save. It requests `world.save` using the `lossless-json` encoding so disk persistence is based on a fresh authoritative snapshot from the Python runtime.

The engine returns the opaque serialized snapshot plus presentation-safe metadata. Godot adds only the local `saved_at` timestamp and passes both values to `WorldSaveStore`.

## Load flow

Loading is deliberately two-stage:

1. `WorldSaveStore` reads and validates only the client-owned envelope and returns the opaque snapshot string.
2. `WorldSavePanel` submits that exact string through `world.load` with the currently displayed world sequence as `expected_sequence`.

The UI does not replace its current world snapshot while the file is being read or while `world.load` is pending. Rejected, malformed, stale, or disconnected loads therefore leave the active campaign unchanged.

After the engine accepts `world.load`, the existing Adventure command-payload reconciliation path applies the returned structured authoritative `world_snapshot` and refreshes world queries.

## Disconnect recovery

The state coordinator exposes bridge disconnect lifecycle to presentation owners. If a disconnect or bridge unbind occurs while a `world.save` query or `world.load` command is pending, `WorldSavePanel` clears its network-operation flags immediately and surfaces a reconnect message. Local disk work remains independently tracked by `WorldSaveStore`.

This prevents a dropped connection from leaving the Save/Load tab permanently disabled.

## Scene ownership

The implementation is split into focused client components:

- `world_save_store.gd` — bounded threaded local persistence only;
- `world_save_panel.gd` / `.tscn` — slots, bridge requests, metadata, errors, disconnect recovery, and load intent;
- `world_rpg_save_view.gd` — thin integration adapter that forwards client-state and accepted world snapshots to the panel;
- `world_rpg_view.gd` — existing Adventure presentation and world-command behavior remains otherwise unchanged.

This avoids turning the already broad Adventure view into a filesystem owner.

## Validation

`res://tests/world_save_load_tests.gd` covers:

- rejection of non-whitelisted slot IDs;
- Save Game requesting `world.save` with `lossless-json` encoding;
- threaded local write and read completion;
- persistence of an opaque snapshot string containing 64-bit RNG digits;
- persisted slot metadata;
- Load Game submitting `world.load` with the exact persisted string;
- current world sequence used as `expected_sequence`;
- no optimistic replacement before engine acceptance;
- bridge-disconnect recovery for pending save UI state;
- accepted world-load payload reconciliation through the Adventure view;
- Save/Load tab scene wiring.

`tests/test_world_bridge.py` covers the lossless bridge representation through a JSON wire round trip and verifies restored RNG data remains exact.

`tests/test_godot_world_save_schema.py` validates a representative envelope containing a canonical `WorldRuntime.snapshot()` string against the versioned JSON Schema.

The Godot save/load suite is part of `scripts/local_ci.sh`.

## Compatibility and follow-ups

This phase extends the existing `world.save-replay.v1` capability without removing the prior structured world-snapshot flow. The production Godot persistence path uses the lossless representation because it is safe across the JSON transport boundary.

Follow-up work remains separately scoped:

1. autosave/checkpoint policy after campaign transitions are stable;
2. explicit migration handlers when a future client envelope or world snapshot version requires them;
3. export/import or cloud synchronization only when product scope requires cross-device saves;
4. end-to-end campaign completion acceptance that includes save, process restart, restore, and continued deterministic play.
