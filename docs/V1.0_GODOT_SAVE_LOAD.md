# v1.0 Godot production save/load UX

## Scope

This v1.0 client phase adds production manual save/load UX to the Godot Adventure view without moving campaign authority or save validation into GDScript.

The feature is intentionally narrow:

- three local manual save slots;
- engine-produced world snapshots;
- threaded local persistence under `user://`;
- a versioned Godot save envelope around the opaque engine snapshot;
- engine-validated `world.load` before any loaded state is presented as authoritative;
- user-visible slot metadata, errors, busy state, and backup recovery.

Autosaves, cloud synchronization, cross-device export/import, and broad save migration tooling remain future product work.

## Authority boundary

```text
Save Game
   |
   v
Godot Save/Load panel
   |
   | query: world.save
   v
Authoritative Python world runtime
   |
   | world_snapshot
   v
WorldSaveStore worker thread
   |
   v
user://saves/world/slot-N.json

Load Game
   |
   v
WorldSaveStore worker thread
   |
   | persisted world_snapshot
   v
Godot Save/Load panel
   |
   | command: world.load + current expected_sequence
   v
Authoritative Python world runtime
   |
   | validate schema/campaign/RNG/references/events/sequence
   v
accepted world_snapshot
   |
   v
Adventure presentation reconciles
```

Godot never applies a snapshot merely because a local file parsed successfully. The local file is untrusted input. `world.load` remains the authoritative validation and replacement boundary.

## Local envelope v1

The client stores a small wrapper around the snapshot returned by `world.save`:

```json
{
  "format": "godot-dnd-world-save",
  "format_version": 1,
  "slot_id": "slot-1",
  "metadata": {
    "saved_at": "2026-08-22 18:00:00",
    "campaign_id": "campaign:local-dev",
    "sequence": 12,
    "area_id": "area:old-road",
    "area_name": "Old Quarry Road"
  },
  "world_snapshot": {}
}
```

`schemas/v1/godot-world-save-envelope.schema.json` versions this client-owned wrapper. The nested `world_snapshot` is deliberately opaque to the client schema because its semantics, compatibility, and validation remain owned by the Python world runtime.

Changing the envelope semantics requires a new `format_version` or an explicit migration. Existing versions must not be silently reinterpreted.

## Slot and path safety

The production UI exposes only these fixed IDs:

- `slot-1`;
- `slot-2`;
- `slot-3`.

The store never derives a path from arbitrary player text. This prevents save-slot path traversal and keeps filenames stable for future migrations.

Save files are bounded to 32 MiB before parsing or writing. Unsupported envelope versions, malformed JSON, mismatched slot IDs, invalid top-level types, and missing snapshots fail closed with a user-facing error.

## Non-blocking disk I/O

`WorldSaveStore` performs directory creation, JSON encoding/decoding, file reads, file writes, and replacement work on a low-priority Godot `Thread` rather than the frame-critical main thread.

Only one save-store operation may run at a time. Completion is deferred back to the main thread before UI signals are emitted. Scene-tree/UI access remains on the main thread.

The store uses a replacement flow:

1. encode and size-check the envelope;
2. write `slot-N.json.tmp`;
3. flush and verify the write;
4. move an existing final file to `slot-N.json.bak`;
5. rename the temporary file to the final slot path;
6. remove the backup after successful replacement.

If a final save is missing but its backup remains, reads can recover the backup and expose that fact in slot metadata.

## Save flow

`WorldSavePanel` does not serialize its cached `_world_snapshot` directly when the player presses Save. It first requests `world.save` so the bytes written to disk come from the current authoritative runtime at save time.

The engine response is wrapped with presentation-only metadata and passed to `WorldSaveStore`.

## Load flow

Loading is deliberately two-stage:

1. `WorldSaveStore` reads and validates only the client-owned envelope.
2. `WorldSavePanel` submits the nested snapshot through `world.load` with the currently displayed world sequence as `expected_sequence`.

The UI does not replace its current world snapshot while the file is being read or while `world.load` is pending. Rejected or stale loads therefore leave the active campaign unchanged.

After the engine accepts `world.load`, the existing Adventure command-payload reconciliation path applies the returned authoritative `world_snapshot` and refreshes world queries.

## Scene ownership

The implementation is split into focused client components:

- `world_save_store.gd` — bounded threaded local persistence only;
- `world_save_panel.gd` / `.tscn` — slots, bridge requests, metadata, errors, and load intent;
- `world_rpg_save_view.gd` — thin integration adapter that forwards client-state and accepted world snapshots to the panel;
- `world_rpg_view.gd` — existing Adventure presentation and world-command behavior remains unchanged.

This avoids turning the already broad Adventure view into a filesystem owner.

## Validation

`res://tests/world_save_load_tests.gd` covers:

- rejection of non-whitelisted slot IDs;
- Save Game requesting `world.save`;
- threaded local write and read completion;
- persisted slot metadata;
- Load Game submitting `world.load`;
- current world sequence used as `expected_sequence`;
- persisted authoritative snapshot passed unchanged to the load command;
- no optimistic replacement before engine acceptance;
- accepted world-load payload reconciliation through the Adventure view;
- Save/Load tab scene wiring.

`tests/test_godot_world_save_schema.py` validates a representative envelope containing a real `WorldRuntime.snapshot()` against the versioned JSON Schema.

The Godot save/load suite is part of `scripts/local_ci.sh`.

## Compatibility and follow-ups

This phase does not change the engine world snapshot schema or the `world.save-replay.v1` bridge contract. It consumes the existing contract.

Follow-up work should remain separately scoped:

1. autosave/checkpoint policy after campaign transitions are stable;
2. explicit migration handlers when a future client envelope or world snapshot version requires them;
3. export/import or cloud synchronization only when product scope requires cross-device saves;
4. end-to-end campaign completion acceptance that includes save, process restart, restore, and continued deterministic play.
