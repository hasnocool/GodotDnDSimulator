# v1.0 Godot Party and Inventory Interactions

## Scope

This phase advances the v1.0 Adventure overlay from read-only campaign management into a usable party and equipment surface while preserving the headless world runtime as the authority.

The Godot client now:

- restores the Journal, Map, Party, and Inventory management tabs on the integrated main-line world view;
- renders party cards from authoritative `characters.get` records instead of showing actor IDs alone;
- displays character name, level, species/background/class identifiers, current/max HP, armor class, and authoritative world equipment assignments;
- renders party inventory counts and currency from the isolated world snapshot;
- lets the player choose an active-party actor, an owned item, and an equipment-slot ID, then submits `inventory.equip` through the normal typed command bridge;
- refreshes world snapshot, actions, journal, map, and party data after accepted world commands rather than mutating the UI optimistically.

## Authority boundary

Godot remains presentation and intent collection only.

The client does not decide whether an actor belongs to the party, whether the party owns an item, whether the expected world sequence is current, or whether the equipment command is accepted. It submits the selected actor/item/slot as intent and waits for the authoritative world runtime response.

The existing world runtime currently validates active-party membership, item ownership, non-empty command fields, and optimistic world sequencing for `inventory.equip`. Equipment-slot compatibility is not yet represented as an engine-provided legal-choice query, so this client phase deliberately treats the slot text as opaque engine intent rather than hardcoding item/slot rules in GDScript.

The world snapshot remains isolated from the tactical/core `AuthoritativeMirror`. Character records are presentation data fetched through `characters.get`; they do not become a second mutable character state in Godot.

## Query and command flow

Opening or refreshing the Adventure overlay requests:

- `world.snapshot`;
- `world.actions`;
- `world.journal`;
- `world.map`;
- `world.party`.

For each active party member without a cached presentation record, the client additionally requests:

- `characters.get { actor_id }`.

Equipment changes use:

```text
Inventory tab selection
  -> actor_id + item_id + slot
  -> inventory.equip
  -> authoritative validation/events/snapshot
  -> world refresh
  -> party/inventory presentation reconciliation
```

## Testing

`res://tests/world_rpg_tests.gd` now covers:

- map and party management queries through the bridge;
- per-party-member `characters.get` queries;
- rendering authoritative character names, HP, AC, and equipment in party cards;
- rendering authoritative inventory counts and journal/map state;
- submitting `inventory.equip` with the selected actor, owned item, slot intent, and isolated world sequence;
- preserving the regression that world state never replaces the tactical/core authoritative mirror.

## Follow-up phases

The next v1.0 Godot-client slices should build on this work:

1. production save/load UX using `world.save-replay.v1` with non-blocking file I/O;
2. engine-provided equipment-slot/item compatibility choices so the UI can replace the opaque slot field with authoritative legal options;
3. richer item presentation metadata and sell/trade controls without client-side price or ownership rules;
4. map navigation/area-selection UX that still delegates travel legality to `world.travel`;
5. end-to-end save/restore and campaign-completion headless Godot acceptance coverage.
